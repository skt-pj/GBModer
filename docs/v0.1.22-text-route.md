# GBModer v0.1.24 — selectable text-recognition route and scroll synchronization

- Processing order remains: capture -> downsample to selected resolution -> image filter -> Accessibility text replacement -> overlay presentation.
- UI keeps both capture routes: MediaProjection (existing route) and Accessibility Window (Android 14+).
- Text recognition / 8x8 redraw remains independently switchable and defaults OFF.
- v0.1.23 attempted stale-frame rejection, but the Accessibility service XML subscribed only to window-state events, so scroll/content callbacks were not actually delivered.
- v0.1.24 subscribes to view-scroll, window-content, text-change, window-state, and windows-change events in both XML and runtime service configuration.
- Scroll/content mutation increments a content revision and hides the current text-bearing overlay immediately.
- Accessibility Window captures are rejected when their revision changes before processing or presentation.
- MediaProjection now snapshots the same content revision per image, waits for a short quiet period before applying Accessibility text, and rejects a frame when the revision changes before copy or presentation.
- MediaProjection explicitly arms/disarms the Accessibility-service text invalidation state while text recognition is enabled.
- Text size/aspect continues to be derived from each Accessibility node's source-window bounds before mapping into the 160x144 GB framebuffer.
- CI includes a generated-source gate that verifies scroll event subscription, both-route invalidation, revision checks, and the required processing order.
